# 커뮤니티 프로젝트 보안 점검 사항

기획서(`기획서.txt`) 기준으로 페이지·기능별로 반드시 고려해야 할 보안 항목을 정리했습니다.

## 회원가입 / 로그인

- **비밀번호 저장**: 평문 저장 금지. Supabase Auth 사용 시 자체적으로 해싱(bcrypt) 처리되므로 직접 구현하지 말고 Supabase Auth를 그대로 활용
- **이메일 중복 확인**: 가입 시 이메일 중복 여부를 서버(DB) 기준으로 검증 (클라이언트 검증만으로는 우회 가능)
- **비밀번호 정책**: 최소 길이/복잡도 규칙을 프론트뿐 아니라 서버(또는 DB 제약)에서도 검증
- **전화번호 등 개인정보**: 수집 목적이 불분명하면 최소화 검토, 저장 시 노출 범위(다른 회원에게 보이는지) 명확히 정의
- **로그인 시도 제한**: 무차별 대입 공격(Brute-force) 방지를 위한 로그인 실패 횟수 제한/캡차 고려
- **비밀번호 찾기 기능**: 이메일 인증 토큰은 일정 시간 후 만료, 재사용 불가하도록 처리

## 게시물 목록 / 상세

- **작성자 본인 확인**: 수정/삭제 버튼이 "본인에게만 노출"되는 것은 UI 단 처리일 뿐이며, 실제 수정/삭제 요청 시 서버(DB)에서도 요청자 = 작성자인지 반드시 재검증 필요
  → Supabase 사용 시 **Row Level Security(RLS) 정책**으로 `auth.uid() = author_id` 조건을 걸어 DB 레벨에서 차단
- **게시글 내용 XSS 방지**: 본문에 HTML/스크립트 입력이 가능한 경우, 저장 시 sanitize 처리 또는 렌더링 시 이스케이프 처리 (React 사용 시 `dangerouslySetInnerHTML` 사용 자제)
- **사진 업로드**:
  - 업로드 가능한 파일 확장자/MIME 타입 화이트리스트 검증 (이미지 파일만 허용)
  - 파일 크기 제한
  - Supabase Storage 버킷 접근 정책(공개/비공개) 설정 및 업로드 권한을 로그인 사용자로 제한
- **검색 기능**: 검색어를 SQL에 직접 concat하지 않고 파라미터 바인딩 사용 (Supabase 클라이언트 라이브러리 사용 시 기본적으로 안전)

## 댓글 / 대댓글

- 댓글도 게시글과 동일하게 **작성자 본인만 수정/삭제 가능**하도록 RLS 정책 적용
- 댓글 내용도 XSS 방지 처리 동일 적용
- 좋아요 기능은 동일 사용자가 중복으로 여러 번 누르지 못하도록 (user_id + post_id) 유니크 제약 필요

## 마이페이지

- 본인 정보 외 다른 사용자의 정보(내가 쓴 글/댓글 목록 등)를 조회할 수 없도록 RLS로 `user_id = auth.uid()` 조건 적용
- 프로필 수정 시 이메일 변경은 재인증(비밀번호 확인) 절차 권장
- 비밀번호 변경 시 기존 비밀번호 확인 절차 필요

## 공통/인프라

- **인증 토큰 관리**: 세션/JWT 토큰은 `httpOnly` 쿠키 또는 안전한 저장소 사용, `localStorage`에 그대로 저장 시 XSS에 취약
- **API 요청 인가**: 프론트에서 버튼을 숨기는 것만으로는 보안이 되지 않으므로, 모든 CRUD 요청은 서버/DB(RLS)에서 권한 재검증
- **환경변수 관리**: Supabase URL/API 키 중 `service_role` 키는 절대 클라이언트에 노출 금지 (프론트에는 `anon`/`publishable` 키만 사용)
- **HTTPS 적용**: 배포 시 전체 통신 HTTPS로 강제
- **Rate Limiting**: 게시글/댓글 작성, 좋아요 등 스팸/어뷰징 방지를 위한 요청 빈도 제한 고려
